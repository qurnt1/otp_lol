## Périmètre et modèle de preuve

L’interface React expose les pages `dashboard`, `statistics`, `live`, `history`, `settings` et `diagnostics`. Diagnostics n’est pas dans la navigation latérale permanente, il est accessible depuis Avancé et via `#diagnostics` (`frontend/src/app/AppShell.tsx`, `frontend/src/app/routes.ts`). Paramètres comprend les routes `general`, `automations`, `account`, `links`, `shortcuts`, `appearance` et `advanced`.

Le harness navigateur courant ne se limite pas à des composants montés isolément: `frontend/e2e/helpers.ts` démarre un processus FastAPI distinct, sert le bundle de production, traverse les vrais endpoints et le WebSocket applicatif, et dialogue avec un faux client League TLS/WSS piloté par `scripts/e2e/app_server.py`. Le client League est synthétique; aucun scénario ne valide une installation Riot réelle. Les dossiers utilisateur sont temporaires et les requêtes navigateur hors origine sont bloquées. `scripts/e2e/app.integration.spec.mjs` ajoute un scénario traversant redémarrage, stockage, Data Dragon et LCU. Le site marketing est un autre projet Vite sous `website/`, avec son propre E2E.

Pour chaque scénario produit, la preuve recherchée suit le geste clavier/souris, le feedback visible, la requête FastAPI et la relecture de l’état persisté ou l’effet LCU attendu. La couverture native reste séparée. Les scénarios positifs de succès utilisent FastAPI et ses données réelles dans le profil E2E; le faux LCU contrôle uniquement l’état externe de League. Les tests de panne listés ci-dessous emploient `page.route` pour retarder ou injecter une panne HTTP/transport locale, ils vérifient le comportement React de récupération et ne prouvent pas que le serveur FastAPI lui-même a émis cette panne. `helpers.ts` bloque aussi les origines Internet, ce qui n’est pas une injection de réponse API.

Priorités: **P0** bloque l’usage ou peut appliquer une action LoL indésirable; **P1** est un parcours principal ou une protection de données; **P2** est une transition rare, le confort ou une couverture secondaire. La suppression des tests Vitest frontend est déjà faite; le tree courant utilise Playwright pour ces suites. « Couvert dans le code » ne signifie pas que toute combinaison d’états a été exercée. Le full browser final a passé 174/174 après les modifications des specs Dashboard, Settings, Statistics et LCU. L’API E2E a passé 45/45 sur six configurations; full-stack 1/1 en 21,6 s. `npm run typecheck`, `npm run api:check`, `npm run build`, `py_compile`, `ruff check` et `git diff --check` passent. Le formatage Ruff complet de `app_server.py` et `fake_lcu.py` échoue sur du formatage préexistant, les ajouts ont été alignés manuellement. Website 13/13 reste un résultat antérieur. Les targeted runs `api-contract` 19/19 et `LCU API` 5/5 sont des sous-runs, pas des tests additionnels à sommer. Les observations natives finales concernent le source WebView en profil isolé: seconde instance du même profil quittant avec code 0 pendant que la primaire et son port restent actifs (DESK-02); ouverture nominale des dossiers Logs/AppData (SET-13); plein écran puis retour fenêtre observés visuellement sans preuve de résolution de la Promise JS (SET-15/DESK-05); annulation/sauvegarde du rapport Diagnostics avec JSON parsable (DIAG-06, aussi partiellement DESK-06). Le provider web n’a pas été exercé faute d’identité (`account_unavailable`). Alt+C/P via injection CUA n’a pas prouvé les hotkeys globaux (DESK-04); le tray reste inconclusif (DESK-03). Ces résultats ne valident ni l’EXE packagé ni League réel. Le self-test du package Windows en CI ne valide pas l’interface EXE interactive.

### Interceptions des scénarios d’échec browser

Les succès de lecture et de mutation utilisent FastAPI réel. Les `page.route` ciblant l’API locale injectent une panne de transport/réponse pour tester le retour UI: `GET /api/bootstrap` (deux réponses 503 avant le bouton Retry), `GET /api/history?limit=250` (deux 503 avant Retry), `GET /api/links/stats` et `/api/links/live` (503 initial), `GET /api/champions` (deux 503 avant Retry), `GET /api/runes` et `/api/skins/86` (chargement contrôlé puis 503), `PATCH /api/presets/pick_1` (503), `GET /api/assets/skins/86/86013/splash*` (abort), `DELETE /api/history` (503 retardé), `GET /api/diagnostics` et `POST /api/diagnostics/run` (503 initial), `PATCH /api/settings` (abort/422, 503 ciblé sur la copie d’identité, et délai contrôlé pendant un toggle), `DELETE /api/settings/last-detected-account` (503 ciblé), `POST /api/presets/reset`, `/api/presets/clear` et `/api/settings/reset` (503 au premier appel), ainsi que `GET /api/network/status` (attente contrôlée puis abort). Les retries réussis désactivent l’interception avant de relire FastAPI; le test History vérifie aussi deux échecs initiaux exactement puis un GET 200 après retrait de la route. Pour Settings, le premier rendu lit `/api/bootstrap`, qui hydrate les caches settings/presets; il n’y a pas de GET initial séparé de `/api/settings` ou `/api/presets`. Ces injections testent le retour UI, pas une panne réellement émise par FastAPI. Le contexte bloque les origines Internet, ce qui empêche l’egress mais n’injecte pas de réponse API.

## Contrats API FastAPI distincts des gestes UI

## Garde-fous d’acceptation de la suite

- Les actions utilisateur sont jouées depuis la vraie interface avec rôle/label et clavier quand pertinent; locator CSS fragile seulement lorsqu’aucun contrat accessible n’existe.
- Pour une mutation, attendre HTTP success puis relire l’API, la persistance après reload/restart et la mise à jour UI; ne valider pas uniquement un toast optimiste.
- LCU: inspecter requête réelle vers le serveur synthétique et le state snapshot après; tester aussi refus/état invalide et vérifier que le texte de succès n’apparaît pas.
- Erreurs: injecter échec au boundary correspondant, vérifier le message, la réversibilité et que les actions désactivées sont réellement désactivées.
- Desktop natif: isoler `APPDATA`, `LOCALAPPDATA`, `TEMP`, port, processus et shell actions; observer HWND/processus/bridge; ne pas toucher au League client utilisateur ni lancer l’EXE produit sans isolation.

Garder screenshots seulement quand fixtures reproductibles; vérifier en plus dimensions, scroll et images `naturalWidth`.
