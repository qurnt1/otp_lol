## Périmètre et modèle de preuve

L’interface React expose les pages `dashboard`, `statistics`, `live`, `history`, `settings` et `diagnostics`. Diagnostics n’est pas dans la navigation latérale permanente, il est accessible depuis Avancé et via `#diagnostics` (`frontend/src/app/AppShell.tsx`, `frontend/src/app/routes.ts`). Paramètres comprend les routes `general`, `automations`, `account`, `links`, `shortcuts`, `appearance` et `advanced`.

Le harness navigateur courant ne se limite pas à des composants montés isolément: `frontend/e2e/helpers.ts` démarre un processus FastAPI distinct, sert le bundle de production, traverse les vrais endpoints et le WebSocket applicatif, et dialogue avec un faux client League TLS/WSS piloté par `scripts/e2e/app_server.py`. Le client League est synthétique; aucun scénario ne valide une installation Riot réelle. Les dossiers utilisateur sont temporaires et les requêtes navigateur hors origine sont bloquées. `scripts/e2e/app.integration.spec.mjs` ajoute un scénario traversant redémarrage, stockage, Data Dragon et LCU. Le site marketing est un autre projet Vite sous `website/`, avec son propre E2E.

Pour chaque scénario produit, la preuve recherchée suit le geste clavier/souris, le feedback visible, la requête FastAPI et la relecture de l’état persisté ou l’effet LCU attendu. La couverture native reste séparée. Les scénarios positifs de succès utilisent FastAPI et ses données réelles dans le profil E2E; le faux LCU contrôle uniquement l’état externe de League. Les tests de panne listés ci-dessous emploient `page.route` pour retarder ou injecter une panne HTTP/transport locale, ils vérifient le comportement React de récupération et ne prouvent pas que le serveur FastAPI lui-même a émis cette panne. `helpers.ts` bloque aussi les origines Internet, ce qui n’est pas une injection de réponse API.

Priorités: **P0** bloque l’usage ou peut appliquer une action LoL indésirable; **P1** est un parcours principal ou une protection de données; **P2** est une transition rare, le confort ou une couverture secondaire. La migration a supprimé les tests Vitest frontend de `src/`; le tree courant utilise Playwright pour ces suites. « Couvert dans le code » ne signifie pas que le test Playwright correspondant a passé. Le dernier run sériel communiqué à l’orchestrateur concernait les tests Python, pas Playwright; les changements browser récents restent à valider.

### Interceptions des scénarios d’échec browser

Les succès de lecture et de mutation utilisent FastAPI réel. Les seuls `page.route` ciblant l’API locale injectent une panne de transport/réponse pour tester le retour UI: `GET /api/champions` (503), `PATCH /api/presets/pick_1` (503), `GET /api/assets/skins/86/86013/splash*` (abort), `DELETE /api/history` (503 retardé), `PATCH /api/settings` (abort, 422 texte et 503), et `GET /api/network/status` (attente contrôlée puis abort). Les retries après retrait de la route reviennent à FastAPI. Le contexte bloque les origines Internet, ce qui empêche l’egress mais n’injecte pas de réponse API.

## Contrats API FastAPI distincts des gestes UI

Ces scénarios sont des tests boîte noire HTTP/WebSocket avec le FastAPI réel. Ils ne représentent pas des actions utilisateur et ne sont pas comptés dans les 66 identifiants de la matrice. Le code est présent, mais cette suite n’a pas été exécutée dans cet audit.

## Gaps et limites vérifiés dans le tree courant

La colonne « Couverture actuelle » décrit les interactions et assertions visibles dans les fichiers présents. Elle ne certifie pas leur réussite: le tree browser récent n’a pas encore été validé par un run Playwright complet.

1. **HIST-02 reste un défaut produit connu:** `history.spec.ts` garde un `test.fail` pour l’absence d’invalidation live après `ready_check_accepted`; les lignes History n’apparaissent qu’après rechargement/remontage. Ne pas retirer ce marqueur avant correction et validation.
2. **Le filtre Historique « Erreurs » est exercé vide.** Aucune action utilisateur normale ne produit l’événement d’erreur requis; la matrice ne fabrique pas d’événement par `page.request` et ne prétend donc pas couvrir un résultat non vide.
3. **Les erreurs UI et les contrats API sont deux preuves distinctes.** Les échecs `page.route` listés plus haut vérifient le feedback React lors d’une panne injectée. `api-contract.spec.mjs` ajoute des requêtes noires au vrai FastAPI pour les 422, l’échec fichier, CORS/Host et l’Origin WebSocket; les 5/5 cas de cette suite ont passé, dans l’agrégat API 23/23. Ce ne sont pas des gestes UI.
4. **WEB-01 n’est que partiellement prouvée:** l’E2E browser constate la limite de manager et l’action native source ne couvre que le retour `network_unavailable` avec egress neutralisé. Elle ne valide pas création/réutilisation/visibilité réussie d’une fenêtre provider.
5. **Actions native-only:** Chromium n’établit pas le fonctionnement du vrai WebView2, tray, HWND, raccourcis globaux, DPI Windows, fermeture/cleanup natif ou dialogues OS. Le runner natif source observe quelques actions (dont provider externe et AppData), mais n’exerce pas le bouton Logs; son exécution et la couverture EXE packagé doivent être rapportées séparément.
6. **League réel non testé:** LCU-01 utilise un faux processus TLS/WSS contrôlé. Il ne couvre ni lockfile/installation Riot réels ni variations de versions du client.
7. **Visuel:** les specs mesurent overflow et géométrie aux résolutions marquées, et vérifient le chargement d’images; aucun défaut visuel n’est confirmé dans ce travail. `deviceScaleFactor` à 125/150 % reste une simulation Chromium, pas un test du DPI système.
8. **Résultats finaux locaux:** les 115/117 et deux échecs de teardown sont historiques. Les runs finaux ont passé browser 130/130, API 23/23 et website 13/13 dans une copie isolée. Ces résultats ne valident pas les parcours natifs ni l’EXE interactif.

## Validation à effectuer avant de déclarer la couverture complète

1. Rejouer les suites Playwright UI frontend, API (`npm run test:e2e:api`) et website sur le tree final; rapporter séparément les configs et toutes les attentes `test.fail`.
2. Pour les mutations: confirmer le geste accessible, le succès API réel, l’état relu et le rendu. Conserver l’étiquette de panne injectée pour tout `page.route` local.
3. Corriger puis rejouer HIST-02 si la réactivité live est attendue; autrement garder le défaut explicitement accepté, sans compter le test expected-fail comme preuve de succès.
4. Exécuter le runner natif seulement dans son environnement Windows isolé; distinguer source/WebView2/Win32/LCU réel et EXE packagé. Ne pas déduire la couverture native du navigateur.
5. Examiner les filtres CI séparément après la migration, notamment les changements de harness, scripts, snapshots, website et runner natif.

## Garde-fous d’acceptation de la suite

- Les actions utilisateur sont jouées depuis la vraie interface avec rôle/label et clavier quand pertinent; locator CSS fragile seulement lorsqu’aucun contrat accessible n’existe.
- Pour une mutation, attendre HTTP success puis relire l’API, la persistance après reload/restart et la mise à jour UI; ne valider pas uniquement un toast optimiste.
- LCU: inspecter requête réelle vers le serveur synthétique et le state snapshot après; tester aussi refus/état invalide et vérifier que le texte de succès n’apparaît pas.
- Erreurs: injecter échec au boundary correspondant, vérifier le message, la réversibilité et que les actions désactivées sont réellement désactivées.
- Desktop natif: isoler `APPDATA`, `LOCALAPPDATA`, `TEMP`, port, processus et shell actions; observer HWND/processus/bridge; ne pas toucher au League client utilisateur ni lancer l’EXE produit sans isolation.
- Visuel: garder assertions layout/overflow à 800×540, 1100×760, 1366×768, 1920×1080, 2560×1440, 2560×1600 et DPR browser 1.25/1.5. `deviceScaleFactor` ne démontre pas DPI Windows réel. Garder screenshots seulement quand fixtures reproductibles; vérifier en plus dimensions, scroll et images `naturalWidth`.
- Chaque scénario E2E doit être idempotent et nettoyer ses processus. Aucun compte réel, export personnel, log, cache utilisateur ou screenshot privé ne va dans les fixtures.
- Les succès browser sont présents dans les specs source mais restent à rejouer après les modifications récentes. Le dernier résultat communiqué est celui du run Python, 115 passés et 2 échecs de teardown; il ne valide pas Playwright.
