# Migration des tests Python vers les E2E, état du 30 septembre 2026

Ce document garde l’inventaire du snapshot avant suppression et décrit l’état courant après le passage explicite à une validation E2E-only. Les workflows du commit de base `e5e61c7` et ceux du working tree actuel sont distingués. Ce plan ne présente pas un E2E présent comme une preuve d’exécution.

## Portée et faits vérifiés

- Avant leur suppression le 30 septembre 2026, `tests/` contenait 27 modules `test_*.py`, soit 389 fonctions ou méthodes dont le nom commence par `test_` (inventaire AST; les cas `subTest` ne sont pas comptés séparément). Les 27 modules, `tests/fake_lcu_server.py` et `tests/__init__.py` ont ensuite été supprimés du working tree conformément au mandat E2E-only.
- Les suites supprimées utilisaient `unittest.TestCase`; elles pouvaient être lancées par unittest et pytest. Aucun `pytest.ini`, `pyproject.toml`, `setup.cfg`, `tox.ini`, `conftest.py` ou `.coveragerc` source n’a été trouvé; aucune mesure de couverture n’était déclarée.
- Au début de la migration, `requirements-test.txt` déclarait `requirements.txt`, `httpx~=0.28` et `pytest~=9.1`. L’agent CI a supprimé `requirements-test.txt` et le pin httpx de `requirements-constraints.txt`; la recherche des workflows et chemins de configuration actifs ne trouve plus pytest/unittest.
- `docs/development.md` a été actualisé pour les commandes Playwright `npm run test:e2e` et `npm run test:e2e:api`; la commande unittest citée dans l’inventaire initial n’est plus un parcours courant.
- Au commit de base `e5e61c7`, `python-ci.yml` lançait `python -m pytest -q` et `release.yml` lançait `python -m unittest discover -s tests -v`.
- Dans le working tree courant, `python-ci.yml` ne lance pas pytest/unittest: il compile les sources puis exécute Ruff. Le workflow Release compile Python, vérifie OpenAPI, exécute les E2E navigateur et API puis fait un self-test headless de l’EXE; il ne lance pas le runner natif ni une UI packagée.
- `frontend-ci.yml` exécute les E2E navigateur et `npm run test:e2e:api`. Ce script appelle en série les configs `account-api`, `asset-api`, `diagnostics-api`, `lcu-automation-api`, `datadragon-cache-api` et `api-contract`, chacune sous `scripts/e2e/`.
- Les sondes de données Data Dragon et fournisseur live ont été supprimées avec leurs modules Python; aucune requête aux services réels ne fait partie de la suite E2E déterministe. Les fixtures locales vérifient le comportement du client face à des réponses contrôlées, pas la fraîcheur du service Riot ou la politique Cloudflare du fournisseur.
- Le harnais full-stack démarre le vrai bundle React compilé et FastAPI, isole le profil, et utilise le vrai `lcu-driver` contre un League synthétique. `scripts/e2e/native/run_native_e2e.mjs` existe pour pywebview/WebView2 sous Windows, mais il n’est pas dans `test:e2e:api` ni les gates CI courantes.
- Le tree a reçu des changements E2E pendant l’audit. Aucun run complet d’intégration n’a été lancé après le dernier gel demandé par le root; les nouvelles specs décrites ci-dessous restent non vérifiées par ce run final.

## Commandes et responsabilités actuelles

| Usage | Commande actuelle | Ce que cela prouve | Limite |
|---|---|---|---|
| Python CI | `.github/workflows/python-ci.yml`: `compileall` + Ruff | Compilation et règles statiques configurées | Aucun test de comportement Python n’est lancé par ce workflow |
| Browser E2E | Depuis `frontend/`, `npm run test:e2e -- --workers=1` | UI React compilée servie par FastAPI, interactions navigateur et fixtures | Pas pywebview, tray, fenêtres natives, hook global ou vraie installation League |
| Full-stack E2E | Depuis `frontend/`, `npx playwright test --config ../scripts/e2e/playwright.config.mjs --workers=1` | FastAPI réel, stockage isolé, restart, vrai transport LCU/TLS/WSS et processus League synthétique | Ne prouve pas le client League réel ni toutes ses phases |
| API E2E | Depuis `frontend/`, `npm run test:e2e:api` | Six configs Playwright sérielles appellent FastAPI réel, fake LCU ou Data Dragon contrôlé selon le scénario | Les scénarios API ne sont pas des gestes UI; certaines propriétés internes sont volontairement abandonnées |
| E2E natif source | `node scripts/e2e/native/run_native_e2e.mjs` | Peut piloter le launcher source, fenêtre WebView2/Win32, tray, raccourcis, dialogs et processus Windows | Exige Windows/WebView2; le runner n’est pas gate CI et ne lance pas le paquet distribué |

`mypy` et `pyright` ne sont pas déclarés par les fichiers de dépendances ni les scripts de validation repérés. Ruff et `compileall` sont des contrôles statiques/compilation, pas des parcours E2E. Le workflow Release fait un build onedir et un self-test headless de l’EXE, mais ne prouve pas les parcours dans son interface packagée.

## Règle de migration

Un test E2E de remplacement doit démarrer l’application réelle, exercer une action via son interface (ou, pour un contrat sans écran, appeler son endpoint HTTP réel comme client externe), puis vérifier un résultat observable: texte/état UI, réponse FastAPI, fichier persisté après redémarrage, événement WebSocket, requête reçue par le faux LCU, fenêtre/processus natif, ou contenu du paquet produit. Les fixtures doivent se trouver à la frontière d’un système externe (LCU, provider Internet, données versionnées, système de fichiers isolé), pas remplacer la logique métier qu’on veut éprouver.

La migration vers « E2E seulement » ne peut pas garder une couverture identique par simple traduction des assertions internes en clics. Plusieurs garanties ci-dessous n’ont aucun rendu UI. Les couvrir honnêtement exige une vérification boîte noire de l’API, des fichiers, du processus natif ou du paquet. Si le périmètre est limité aux actions d’un utilisateur dans l’interface, ces garanties deviennent explicitement non couvertes; elles ne doivent pas être présentées comme migrées.

### Garanties qui restent couvertes uniquement au niveau observable

- Les réponses des endpoints account, assets, diagnostics et settings peuvent être vérifiées comme sorties HTTP de l’application réelle. Les routes account stats n’ont pas de page utilisatrice; ces scénarios sont des contrats de consommateur API, pas une validation visuelle.
- Le fixture LCU traverse le vrai transport HTTP/TLS/WSS et les callbacks applicatifs. Les nouveaux cas observent directement mutations, corps de requête, événements et état final; ils ne prouvent pas le comportement face à chaque version réelle de League.
- Le cache Data Dragon prouve un fetch puis la réutilisation après restart hors ligne pour un catalogue valide. La preuve ne couvre pas les algorithmes internes de cooldown, single-flight sous concurrence, corruption partielle ou données Riot live.
- Le profil temporaire rend certaines écritures et redémarrages observables; il ne remplace pas les assertions exactes sur la séquence `fsync`/`os.replace`, les locks Python, la mutation de copies, ni chaque état privé des dataclasses.
- La fenêtre native, WebView2, tray, hooks clavier, DPI multi-écran et dialogues restent au-delà du Chromium. Le runner natif existe, mais n’est pas exécuté ni gate dans les workflows constatés; le self-test headless de l’EXE ne couvre pas les gestes UI natifs.

### Garanties internes explicitement abandonnées ou non équivalentes

Les suites sont supprimées malgré ces assertions, comme demandé pour l’objectif E2E-only. Le registre précédent contient les noms exacts des méthodes perdues. Il n’existe pas de preuve E2E équivalente pour:

- la copie défensive/rollback des objets mémoire, l’ordre précis de verrous, le comportement de writers concurrents et tous les scénarios `os.replace`/atomic write;
- toutes les branches retries/timeout/confirmation de champ de champion select, de sorts et de skins, la concurrence d’applications, le parsing de payloads runes et chaque transition interne de `GameState`;
- les normalisations utilitaires pures, signatures de méthodes privées, comparaison SemVer, tous les encodages Riot ID/URL, et tous les formats de release notes;
- les réponses normalisées de chaque erreur HTTP/JSON/disconnect/timeout dans `LcuClient`, les frames malformées, les locks internes des diagnostics, l’isolation de chaque observer, l’ordre exact des checks de démarrage et la totalité des chemins de redaction;
- les structures versionnées/corrompues de tous les catalogues LCU, rétention de toutes les versions de snapshot, fraîcheur indépendante de chaque image et probes Data Dragon/provider réelles;
- l’ensemble des doubles pywebview/WebView2, branches registre WebView2, fenêtres provider et races native, restauration multi-écran réelle, hotkey hooks en cas de conflit, et chaque défaillance d’instance unique;
- les assertions de `test_release_metadata.py` qui inspectaient directement README, constante de version, spec Inno Setup, workflow YAML, configuration signature/draft, ordre des étapes et captures documentaires. Les workflows/builds actuels sont exécutés par leurs propres jobs, mais la suite Python ne les surveille plus par assertions de source;
- les sondes opt-in sur les pages Data Dragon et fournisseur de statistiques réels. Le déterminisme E2E utilise les fixtures; aucune garantie sur disponibilité, contenu courant ou headers de tierce partie ne reste.

La suppression de ces assertions internes est une limite acceptée par le mandat, pas une affirmation que leurs garanties ont été validées par Playwright. Les lignes de la matrice marquées non couvertes doivent rester visibles dans toute décision release/QA suivante.

### Limites et validations restant à faire

- Aucun E2E n’a été lancé après les changements les plus récents, à la demande du root jusqu’au gel coordonné. Les deux nouvelles configs `lcu-automation-api` et `datadragon-cache-api` ont uniquement reçu une revue statique; elles doivent être incluses au run ciblé final.
- Le nouveau scénario de remplacement de settings exerce une collision contrôlée sur le profil temporaire; il ne prouve pas panne réelle de disque, ACL, antivirus ou concurrence d’écritures.
- Le dernier stress targeted rapporté sur les deux cas Settings avait encore une fuite `api-server-thread-still-alive` sur 1/10 répétitions après l’amélioration harness qui joint le serveur après la fermeture WSS du fake LCU. La cause précise n’est pas établie et aucun code `src/` n’a été modifié. Le run final doit relever explicitement tout résidu.
- Le runner natif et le vrai EXE n’ont pas de preuve d’interaction UI dans cette migration; seules les gates E2E navigateur/API et le self-test packagé sont programmés dans les workflows.
- Le manifeste et le pin de test sont supprimés. Les anciens plans/docs archivés peuvent contenir les commandes historiques; ils ne sont pas des runners actifs. La recherche courante des workflows, configurations et modules `tests/test_*.py` ne retourne aucun runner/suite Python; `unittest.mock` dans le self-test produit reste hors de ce périmètre.

## Verdict

Le working tree ne contient plus de suite Python `test_*.py`; les sorties publiques réalisables disposent de parcours React/FastAPI ou d’API E2E et la commande API E2E est reliée à la CI. Ce basculement supprime toutefois 389 assertions Python, dont plusieurs propriétés internes et cas natifs/live sans équivalent E2E. Les nouveaux scénarios LCU/Data Dragon et les contrats API ne sont pas encore validés par le run final coordonné. L’état est donc **migration de sources effectuée, validation E2E finale en attente, couverture des garanties internes explicitement réduite**.
