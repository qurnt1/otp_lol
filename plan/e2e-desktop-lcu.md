## Frontières de preuve

Il faut conserver quatre niveaux séparés dans les rapports E2E :

1. **Navigateur + FastAPI + LCU synthétique** : `frontend/e2e/` sert le bundle React compilé, démarre le vrai FastAPI avec un profil temporaire, et traverse le vrai WebSocket applicatif. Le faux League répond en TLS/WSS et est injecté dans le scanner de processus pour que le vrai `lcu-driver` et les handlers de production restent actifs. Cela prouve le protocole et les transitions contrôlées, pas la découverte globale ou le comportement d’un vrai client League.
2. **API/full-stack** : `scripts/e2e/*.spec.mjs` appelle le vrai serveur FastAPI et contrôle le client LCU / Data Dragon au bord réseau. `app.integration.spec.mjs` prouve en plus reconnect, redémarrage, persistance et mutations LCU observées. Le filtrage du processus synthétique est une protection intentionnelle.
3. **Source WebView Windows** : `scripts/e2e/native/run_native_e2e.mjs` lance `native_app.py` avec le vrai pywebview/WebView2 et le vrai bridge natif. Il n’exécute pas `OTP LOL.exe`. La matrice des réglages signale un désaccord à reproduire entre l’état du menu tray et Auto-Ban. La tentative du 2026-10-02 a été interrompue par la protection du runner lorsque Brave était la fenêtre au premier plan; les actions tray, raccourcis et fournisseur restent donc non vérifiées dans cette exécution.
4. **EXE / installateur interactifs** : `package-smoke.yml` compile un onedir et lance `--self-test --allow-missing-webview2`. Cela ne prouve pas l’ouverture de la fenêtre WebView, l’installation, les raccourcis, la session WebView persistante ou un vrai League. `docs/release.md` impose un smoke manuel sur l’installateur signé exact avant publication.

Les injections `page.route` prouvent le retour visuel après une panne simulée dans le navigateur; elles ne prouvent pas que FastAPI a réellement émis cette panne. Pour toute affirmation de persistance, l’E2E doit relire l’API ou redémarrer avec le même profil. Pour toute action League, il doit relire l’état de la fixture ou capturer la requête HTTP reçue par le faux LCU, en plus du feedback UI.

## Exécution réelle du runner natif (2026-10-02)

Environnement observé : Python 3.13.7, Node 22.16.0, modules Python `webview` et `fastapi` disponibles, Playwright installé sous `frontend/node_modules`, runtime WebView2 présent. `python scripts/e2e/native/native_app.py --preflight` a terminé avec le code 0 et `{"leagueProcesses":[]}`.

La commande `node scripts/e2e/native/run_native_e2e.mjs` a démarré le vrai `launcher_web.py` source avec pywebview/WebView2, FastAPI et un profil temporaire isolé. Elle a confirmé le bootstrap déconnecté, le HWND natif, le refus d’une seconde instance et l’annulation par Win32 du dialogue natif d’import; le scanner LCU a observé zéro candidat et zéro connexion. Les captures `initial.png` et `settings-advanced.png` sont sous `frontend/test-results/native-e2e/2026-10-02T05-54-22-187Z/`.

La commande s’est terminée avec le code 1 avant la première action tray. Le helper Win32 a refusé l’entrée car la fenêtre au premier plan appartenait au PID 86532, identifié comme Brave affichant YouTube : `Refusing native menu input because the foreground window is outside the isolated app`. Le runner a donc correctement protégé la fenêtre d’une autre application. Le nettoyage a confirmé l’arrêt de l’arbre de processus, des helpers et la suppression du profil temporaire. Ce résultat est une exécution native partielle, pas une gate réussie ni un défaut produit; les actions après l’annulation du dialogue n’ont pas été observées. Ne pas contourner cette garde : relancer sur une session Windows interactive dédiée dont le premier plan reste disponible pour le test.

Une tentative ciblée supplémentaire a appelé `page.bringToFront()`, puis `SetForegroundWindow` sur le HWND OTP de l’arbre isolé et a vérifié le PID foreground avant toute entrée tray. Le premier plan est resté sur Brave (PID 86532); le helper n’a envoyé aucune touche ni clic et a nettoyé l’arbre de processus et le profil temporaires. Cela confirme que `page.bringToFront()` via CDP et cet appel natif n’ont pas obtenu le focus de la fenêtre dans cette session. Une exécution entre ces essais a été refusée au préflight parce que `LeagueClientUx.exe` était présent (PID 31708). Après l’essai de focus, une vérification supplémentaire du préflight a détecté un autre client League (PID 87588), donc aucune nouvelle exécution n’a été lancée. Aucun processus League n’a été arrêté, aucun contournement n’a été ajouté, et les sources du runner ont été laissées sans modification. Les actions tray restent non vérifiées; la suite doit se faire dans une session Windows où OTP peut devenir la fenêtre foreground par une activation autorisée par le système.

## Résidu de test fournisseur non E2E

Les sources actuelles ne contiennent plus le dispatch `--provider-smoke` ni `run_provider_smoke()`; `src/desktop/self_test.py` ne prouve donc pas de comportement provider. `plan_update.md` conserve une ancienne case cochée pour cette commande, uniquement comme historique, sans attester qu’elle existe encore ou s’exécute dans le tree courant.

Aucun E2E actuel ne prouve le cycle de vie d’une vraie fenêtre provider: ouverture, réutilisation, affichage/masquage, reload ou fermeture. Le runner natif présent vérifie des limites d’URL et le refus hors ligne, mais pas le succès du cycle provider; l’essai natif documenté s’est arrêté avant ces actions. La couverture positive du provider est donc une lacune E2E actuelle. Un parcours natif dédié devra l’observer sur WebView2 avant qu’un comportement provider connecté puisse être déclaré validé.

## Commandes de référence

Prérequis des scénarios navigateur/API : Node 22, Python 3.13, environnement E2E isolé selon `docs/development.md`, dépendances installées, puis commandes depuis `frontend/` :

```powershell
npm run build
npx playwright test --workers=1
npx playwright test --config ../scripts/e2e/playwright.config.mjs --workers=1
npm run test:e2e:api
```

Source WebView, sur Windows avec pywebview/WebView2 et session interactive : depuis la racine, `node scripts/e2e/native/run_native_e2e.mjs`. Vérifier le code de sortie, le rapport JSON, les captures et que `OTP LOL.exe` n’a pas été lancé; le runner le vérifie lui-même. Cette commande requiert les dépendances Python et Playwright installées comme indiqué dans les docs.

Package smoke depuis la racine, après `npm run build` dans `frontend/` et installation de `requirements-build.txt` :

```powershell
python create_exe.py --mode onedir --no-shortcut
& ".\OTP LOL\OTP LOL.exe" --self-test --allow-missing-webview2
```

Le gate release manuel prend l’installateur signé généré par le workflow de tag, l’installe sous un compte Windows standard et suit toute la liste `docs/release.md`. Ne pas fusionner les résultats de ces commandes en un seul total : elles couvrent des environnements et frontières différents.

## Gates recommandées

### À chaque PR / push ciblé

Garder les trois jobs actuels : `frontend-ci.yml` (build/type/API générée, navigateur, full-stack restart/LCU, suites API) et `package-smoke.yml` (PyInstaller onedir + self-test). Les specs navigateur et API restent des E2E Playwright même lorsque la panne est injectée côté navigateur; elles ne deviennent pas des tests unitaires. Toute nouvelle action UI critique reçoit au moins une preuve croisée: geste utilisateur → requête FastAPI → état relu ou mutation fake LCU.

### Gate Windows source WebView

Le runner natif doit devenir un gate séparé uniquement après qu’il termine de façon répétable sur un Windows **interactif** dédié, avec WebView2, profil jetable, accès au bureau verrouillé pour ce run, aucun vrai League candidat et egress externe bloqué. Réparer/qualifier d’abord le mismatch tray/Auto-Ban consigné dans la matrice. Une CI GitHub hébergée non interactive ne prouve pas le focus, tray, hotkey globale, dialogue Win32 ou comportement visible; un skip d’environnement ne doit pas apparaître comme couverture réussie.

### Gate EXE/installateur et vrai League avant publication

Garder l’artefact de release en brouillon tant que la checklist de `docs/release.md` n’a pas été exécutée sur l’installateur **signé du tag exact**, WebView2, compte standard et profil jetable. Consigner également les versions OTP/League, pass/fail et logs expurgés. L’interaction League réelle, les variations de patch, le login Riot, DPI/multi-écran et l’installation WebView2 ne sont ni fiables ni sûrs dans les CI partagées; leur preuve est manuelle ou nécessite un poste/runner de qualification dédié. Ne jamais diriger le scanner LCU de CI vers un compte/client personnel.

## Conditions de complétion de ce plan

- Chaque action P0/P1 ci-dessus est soit couverte par un E2E nommé et vérifié, soit clairement maintenue en gate manuelle non simulable.
- Les rapports précisent toujours si l’assertion vient du DOM, de la réponse FastAPI, du faux LCU, du WebView natif source ou de l’EXE installé.
- Les tests de retry/rollback échouent d’abord par une fixture/interception intentionnelle, puis prouvent une reprise avec la vraie app/API; ils ne masquent jamais le statut transport.
- Pas de test n’affirme « vrai League », « EXE interactif » ou « provider réellement chargé » quand il ne lance que React/FastAPI/fake LCU.
- Le runner natif source ne compte comme gate qu’après répétition réussie sans `skippedActions` sur les parcours indispensables et après triage du désaccord tray/Auto-Ban.
- La checklist de publication capture la preuve de l’installateur signé exact, WebView2 et League réel; un build vert seul ne la remplace pas.
