# État de migration des tests frontend vers des parcours E2E

Date de l’inventaire : 2026-09-30.

Snapshot du checkout `codex/react-fastapi-webview-migration`, HEAD `e5e61c7b39d805656fc56b50391a52c74fa11eae`; les changements locaux non commités sont inclus.

Périmètre : état courant de Vitest retiré sous `frontend/src`, Playwright UI sous `frontend/e2e` et `website/e2e`, et scénarios boîte noire API sous `scripts/e2e/*-api.spec.mjs`, scripts npm et configurations associées.

Nature : état de couverture maintenu en complément de `user-action-e2e-matrix.md`. Le registre Vitest en section 9 est une archive de la suite supprimée, pas une liste de travaux à effectuer.

## Résumé vérifié

- Le tree courant ne contient aucun `frontend/src/**/*.test.ts(x)` ni `frontend/src/test/setup.ts`; `frontend/vite.config.ts`, `frontend/package.json`, `frontend/package-lock.json` et le workflow frontend ne référencent plus Vitest, jsdom ou Testing Library. `npm test` n’est plus un script frontend; `test:e2e`, `typecheck`, `api:check` et `build` restent présents.
- Les 17 anciens fichiers et 45 cas Vitest sont supprimés. Leur mapping détaillé plus bas est conservé comme registre historique, pas comme couverture encore en vigueur ni plan de suppression.
- `frontend/e2e` contient 13 specs et 121 appels `test()` statiques, auxquels s’ajoutent les cas produits par les boucles viewport/slot. `website/e2e/site.spec.ts` contient 9 appels `test()` statiques plus sa boucle de viewports. Ces nombres sont un inventaire source, pas un résultat de test.
- `frontend/playwright.config.ts` exécute Chromium Desktop avec trace après échec. `frontend/e2e/helpers.ts` démarre l’application locale via harness, isole les données utilisateur, bloque l’egress navigateur et expose des helpers de lecture API et de pilotage du faux LCU.
- Les parcours positifs utilisent le bundle compilé, FastAPI et le WebSocket applicatif; le client League reste une simulation synthétique TLS/WSS. Les injections `page.route` sont des pannes UI HTTP/transport contrôlées et sont inventoriées dans `user-action-e2e-matrix.md`.
- `scripts/e2e/api-contract.spec.mjs` ajoute cinq scénarios directs HTTP/WebSocket sur le vrai FastAPI: validation 422 et absence de mutation, projection des presets, échec contrôlé du remplacement settings, headers/CORS/Host et refus d’un Origin WebSocket. Ce sont des contrats API boîte noire, pas des actions UI; aucun ne simule un clic React. La commande sérielle est `npm run test:e2e:api` depuis `frontend/`.
- Les actions browser ciblées incluent désormais filtres History, refresh Stats/Live, choix providers, import/export settings, clipboard Diagnostics et écrans aux résolutions demandées. Le code des specs récentes n’a pas encore passé de run Playwright sur le tree courant. Le dernier run Python sériel n’est pas une validation browser.
- HWND, WebView2, tray, raccourcis globaux, dialogues natifs et League installé restent des frontières distinctes et non prouvées par Chromium.

Le retrait des tests Vitest est déjà présent dans le tree courant. La couverture Playwright reste incomplète: la matrice liste les parcours observés et les gaps encore ouverts. Certaines frontières, notamment bridge natif, HWND, DPI Windows et League installé, ne sont pas prouvées par Chromium seul. Le registre ci-dessous garde les anciennes dispositions à titre historique; il ne constitue ni une liste de suppressions futures ni un statut courant.

### Contrats API boîte noire (hors parcours UI)

`npm run test:e2e:api` séquence les specs API dédiées de `scripts/e2e/`, y compris `api-contract.spec.mjs` avec sa configuration `api-contract.config.mjs`. La nouvelle spec utilise `page.request` ou un socket TCP pour parler directement au FastAPI du harness. Les assertions portent sur les réponses HTTP/WebSocket et l’état relu, sans geste d’interface. Elle est présente dans le working tree mais n’a pas été exécutée; le run Playwright final reste nécessaire.

Le cas de persistance provoque une erreur déterministe en occupant le chemin `parameters.toml` avec un répertoire dans un profil temporaire. Il confirme le rollback pour cette branche d’échec seulement. Il ne prouve pas le comportement sur disque plein, ACL, antivirus, écrivain concurrent ou panne système. Les cas de données corrompues qui ne franchissent pas la validation Pydantic et l’acceptation d’un handshake WebSocket valide ne sont pas établis par cette spec.

Pour qualifier un succès, un test part du geste visible puis vérifie l’API/stockage ou l’effet LCU; une lecture `page.request` seule sert d’oracle d’état, elle ne remplace pas le clic. Les tests de panne restent clairement distingués des parcours de succès full-stack. Les modifications récentes listées ici restent en attente d’un run Playwright final.

## 4. Tests purement internes sans action utilisateur directe

Les assertions purement internes ci-dessous ne justifient pas un « E2E » artificiel:

1. Délai exact de reconnexion à 1 000 ms dans `events.test.ts`. Garder seulement la preuve utilisateur de récupération visible après reconnexion. Le backoff exact est une politique interne, non une garantie d’UX.
2. Header `Content-Type` absent sur GET dans `client.test.ts`. C’est une propriété du client HTTP. API generation/typecheck et échanges FastAPI réels couvrent mieux le contrat sans cliquer dans l’UI.
3. Valeur de retour `null`/objet interne de `parseHashRoute`. L’E2E doit vérifier la page résultante et les routes accessibles, pas une structure de données privée.
4. Scan global `content/fr` pour encodage/accentuation. Ce contrôle ne correspond à aucun parcours individuel; le remplacer par la vérification visible de copies importantes ou le déplacer hors de la suite comportementale si le scan global doit survivre.
5. Valeurs host/port/userinfo arbitraires passées directement à `openExternalUrl` s’il n’existe aucun champ utilisateur qui fournit cette chaîne. Maintenir l’URL allowlist comme exigence sécurité via code review/contrat de provider; l’E2E porte sur tous les liens réellement affichés.
6. Actions futures inconnues de `localizeRuntimeStatus`. Si aucun événement de production ne peut les générer, ne pas inventer un endpoint ou une action inaccessible juste pour tester un fallback. Documenter explicitement le contrat qui protège le texte backend.
7. Classe CSS exacte ou compteur de nœuds DOM. Tester le résultat visuel/accessibilité (image visible, texte clair, focus, débordement) et éviter de conserver les assertions sur un arbre de rendu privé.

Les specs Vitest ont été retirées du tree avant que tous ces comportements internes soient remplacés par une preuve équivalente. Le risque résiduel est une baisse de couverture de branches internes; il faut le garder explicite et préserver les contrôles statiques d’API/typage, sans créer de faux parcours utilisateur.

## 5. Règles d’implémentation des parcours

### Fixture et données

- Construire le frontend de production avant Playwright et démarrer le vrai FastAPI via `scripts/e2e/appServer.mjs`. Ne pas basculer ces parcours sur des composants rendus jsdom, un mock `/api/**`, un faux client HTTP ou un remplacement du WebSocket applicatif.
- Utiliser le profil temporaire isolé déjà fourni par `otpApp`; ne jamais amorcer le vrai `%APPDATA%` ou des données de compte personnelles.
- Pour les scénarios connectés, partir du faux client LCU TLS/WSS de `scripts/e2e/fake_lcu.py`. Préparer `phase`, `session`, `pickable_champion_ids`, `pickable_skins`, `rune_pages`, identité et rôle avant de naviguer; émettre la vraie séquence d’événements ensuite.
- Data Dragon/GitHub doivent être fixtureés au boundary externe, et l’egress public doit rester bloqué. Les tests de providers ouvrent une URL interceptée; ils ne chargent pas le site tiers réel.
- Faire les gestes via `page.getByRole` et les labels/accessibles en premier. Les sélecteurs classes déjà nécessaires à la carte peuvent rester secondaires; ajouter un rôle/nom sémantique si l’action ne peut être ciblée autrement.
- Après une mutation, attendre le succès réel, relire `/api/settings`, `/api/presets`, `/api/history` ou l’état LCU, puis vérifier le retour UI. Le texte d’un state optimiste seul ne prouve pas la persistance.
- Pour un scénario d’échec, marquer dans le nom et le rapport la frontière fault-injected. Ne pas remplacer silencieusement FastAPI ou `/api/events` en affirmant que le backend est parcouru.

### Rendus, images et viewport

- Les suites layout couvrent déjà 1366×768, 1920×1080, 2560×1440, 2560×1600, 1100×760 et 800×540; les `deviceScaleFactor` 1.25/1.5 sont simulations Chrome, pas une modification du scaling Windows réel.
- Quand une assertion porte sur un asset, attendre `complete && naturalWidth > 0` et utiliser des fixtures locales distinctes par fichier/champion. Une réponse synthétique identique pour toutes les images ne prouve ni la bonne source ni la sémantique de la preview.
- Les snapshots sensibles au contenu d’images doivent être stables et pris au même état fixture que le run. Ne pas mettre à jour toutes les baselines pour faire passer le test; compléter par bornes, overflow, focus, et assertions de nom/état lisibles.

### E2E native

`frontend/e2e` Chromium ne valide pas un vrai HWND, le focus WebView2, DPI système, tray, raccourci global, lien externe géré par Python ou fenêtre après fermeture. `FE-NATIVE-01` ne peut pas être déclaré couvert par une évaluation JS de `window.pywebview`. Un runner natif source est présent dans `scripts/e2e/native/run_native_e2e.mjs`; il doit être évalué sur Windows séparément, et sa couverture réelle est limitée aux actions qu’il clique et observe. L’exécution CI de ce runner est suivie dans l’audit des workflows.

- Les **45 anciens cas Vitest des 17 fichiers** ont une entrée de disposition dans le registre historique; cela ne signifie pas qu’ils sont tous remplacés par une preuve E2E complète.

- Les parcours utilisateur gardent le vrai bundle construit, FastAPI, le transport WSS applicatif et le `lcu-driver` réel; seuls LCU, Data Dragon/GitHub externes contrôlés et fautes de transport nommées sont simulés.

## 8. Risques

- **Perte de couverture des branches internes :** les 45 cas supprimés étaient compacts; tous leurs invariants internes ne sont pas prouvés par les parcours E2E. Garder cette disposition explicite au lieu de falsifier des états UI.
- **Flakiness/coût :** navigateur + serveur Python + faux LCU sur Windows peut allonger CI; réutiliser la fixture, éviter attentes temporelles, et mesurer la durée avant de retirer les unités.
- **E2E faussement intégrée :** `page.route` sur API locale peut vérifier le feedback d’échec React mais n’exerce pas la réponse FastAPI; étiqueter ces cas. Ne jamais intercepter les chemins normaux `/api/**` pour fabriquer des succès.
- **Bridge inaccessible au navigateur standard :** un mock JS ne validera pas l’ouverture native; tant que WebView2 interactif ne tourne pas de façon automatisée, le résultat complet demandé n’est pas atteint.
- **Données LCU trop simplifiées :** un faux client peut vérifier les règles protocolaires et les transitions programmées, pas tous les états/versionnements d’un vrai client League.
- **Images/snapshots trompeurs :** placeholders visuels ou baselines prises à des états différents peuvent signaler du bruit comme régression ou cacher un fallback cassé.
- **CI verte mais UX incomplète :** `api:check`, `tsc` et build ne prouvent pas les gestes utilisateur; inversement, un browser vert n’établit pas le bon comportement sur League installé ou le desktop natif.
